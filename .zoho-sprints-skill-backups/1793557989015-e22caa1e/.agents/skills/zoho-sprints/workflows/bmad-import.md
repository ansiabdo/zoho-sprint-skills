# Workflow: Approved BMAD planning → Zoho

Use [the policy contract](../references/policy-contract.md), [audit ledger](../references/audit-ledger.md), and [audit continuity](../checks/audit-continuity.md). Run only when the user or trusted project configuration identifies the project as BMAD-managed and points to accessible artifacts. Do not infer BMAD from a folder name alone.

1. Resolve the project's BMAD method/version, approved source artifacts and precedence. Separate approved requirements from drafts, design proposals and assumptions.
2. Map source artifact and stable section ID → capability/epic → independently valuable User Story and criteria → child Task/Bug → test evidence. Use repository-relative references; avoid pasting whole documents into Zoho.
3. Consolidate micro-stories before mapping. Merge candidates only when they share actor, business outcome, epic, release and acceptance surface and each is below 2 points; keep 3–7 combined criteria and every source-section reference. If an “epic” is one sprint-sized deliverable, represent it as one Story under the existing epic container. If a “story” is only a technical step, make it a Task under the real Story. Record the merge/split rationale. See [estimation and priority](../references/estimation-and-priority.md#bmad-micro-story-consolidation).
4. Read existing Zoho scope, the project knowledge base and the local ledger. Compare title, outcome, criteria, parent and source references for duplicates. Present proposed mapping, confidence, eligible sprint, analog-based points, priority rationale and blockers before writes.
5. Resolve assignees from the project's Current Project Team, not from the BMAD author or Git committer: Analyst → Analysis team; main mobile/web/back-end → Assignee by surface. See [project team routing](../references/project-team-routing.md).
6. Apply the configured role rules. Developer children need assigned Stories; new Developer Stories need Zoho Active status and an eligible date window. An approved BMAD artifact is not by itself authorization for an external write.
7. After authorized writes, record actual Zoho IDs and read back. On later runs, compare stable artifact IDs/fingerprints; import only new or changed approved material. If source content changes, show a diff and preserve manual Zoho edits unless a merge is authorized.
8. Leave conflicting, unapproved or ambiguous requirements pending. Report imported, reused, merged, skipped and unresolved mappings with exact source sections and verified Zoho IDs.

Before any create/update apply [field completeness](../references/field-completeness.md). If BMAD or code shows partial/different delivery against an existing Zoho description, use [actual delivery](document-actual-delivery.md): retain the original text byte-for-byte, add the exact separator `##+=================================================##`, then the marked evidence section; BMAD completion does not authorize changing product acceptance criteria. Update the project knowledge base with new mappings, analogs and conflicts. Use [release management](release-management.md) when the imported scope belongs to a release, and [link and clone](link-and-clone.md) when BMAD sections split or continue across sprints.
