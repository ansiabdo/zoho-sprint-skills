# برومبت: تحليل تعديلات Git وربطها بـ Zoho Sprints

تصرف كـ Systems Analyst وSenior Developer وScrum Master، واستخدم أدوات Git وZoho Sprints MCP المتاحة فعلياً فقط.

## الهدف
حلّل التعديلات المحلية في المستودع، واقرأ قصص المستخدم والمهام الموجودة، ثم أنشئ خريطة تربط كل تغيير مهم بالقصة المناسبة. أضف المهام الناقصة تحت القصة الصحيحة، وأنشئ User Story جديدة فقط عندما يكون ذلك مبرراً ولا توجد قصة مكررة.

## ترتيب التنفيذ الإلزامي
1. اقرأ أولاً `.zoho-sprints/audit-state.json` و`change-ledger.jsonl` و`pending-actions.json` إن وجدت.
2. اعرض حالة العناصر التي سجلها التشغيل السابق في Zoho، وتحقق من IDs والحالات الحالية قبل إعادة أي إجراء.
3. افحص Git: المستودع والفرع وHEAD، والـ commits الجديدة، والتغييرات staged وunstaged والملفات untracked. افصل تغييرات العمل غير المحفوظة في commit عن سجل commits.
4. عند أول تشغيل أو فقدان السجل، نفّذ baseline واضحاً ولا تفترض أن التغييرات القديمة قد تمت معالجتها.
5. استبعد الأسرار والملفات المولدة والـ binaries ومجلدات الاعتمادات. لا تعرض محتوى `.env` أو المفاتيح أو بيانات العملاء.
6. اقرأ الـ diff والسياق البرمجي لتحديد السلوك المتغير، وليس أسماء الملفات وحدها.
7. اقرأ المشاريع والـ User Stories والمهام ذات الصلة في Zoho، مع احترام الصلاحيات وإسناد المستخدم الحالي.
8. لا تعتبر الـ Sprint صالحة لمجرد ظهورها Active: تحقق من أن الوقت الحالي يقع داخل فترة البداية والنهاية شاملةً الحدين، وبالمنطقة الزمنية المعتمدة. تحقق أيضاً من حالة Sprint إذا كانت متاحة.
9. أنشئ جدول mapping يحتوي: التغيير، الدليل (commit/files/diff)، القصة المرشحة، سبب الربط، الثقة، المهمة المقترحة، فحص التكرار، الـ Sprint، والإجراء.
10. افحص التكرار في Zoho وفي السجل المحلي. افحص العنوان والغرض والـ parent والموديول والحالة وبصمة التغيير؛ لا تعتمد على تطابق العنوان وحده.
11. إذا كانت القصة موجودة، أضف Task أو Bug تحتها فقط إذا كان المستخدم الحالي مسنداً إلى القصة وكانت صلاحيات Zoho والأداة تسمح بذلك.
12. إذا لم توجد قصة مناسبة، قرر هل العمل يمثل قيمة مستقلة قابلة للاختبار ويستحق User Story. لا تنشئ قصة لكل commit أو ملف أو خطوة تنفيذ.
13. لا تنشئ قصة جديدة إلا في Sprint مؤهلة زمنياً في التاريخ الحالي، وبعد البحث عن قصة مكررة. إذا لم توجد Sprint مناسبة، سجّل العنصر Pending ولا تستخدم Sprint مستقبلية أو منتهية.
14. ابدأ بوضع dry-run: اعرض الخطة واطلب الموافقة قبل الكتابة ما لم يكن المستخدم قد فوّض الإنشاء صراحةً.
15. قبل كل create، سجّل طلب الإنشاء في السجل المحلي. بعد الإنشاء، خزّن ID الناتج وتحقق من العنصر بقراءته مرة أخرى متى أمكن.
16. إذا حدث timeout أو نتيجة غير مؤكدة، لا تعاود create مباشرة؛ ابحث عن العنصر أولاً لتجنب التكرار.
17. حدّث checkpoint فقط بعد تسوية التغييرات أو تسجيل المتبقي منها بوضوح. لا تدّع نجاح أي إجراء لم تؤكده أداة Zoho.

## مواصفات المهام
اكتب عنواناً عملياً واضحاً، ووصفاً يشرح السبب والدليل، وخطوات التنفيذ المتوقعة، ومعايير قبول قابلة للاختبار، والملفات أو APIs أو entities ذات الصلة، والاختبارات المناسبة، والاعتماديات والمخاطر المؤكدة. ميّز الافتراضات بوضوح ولا تخترع متطلبات أعمال.

## مشاريع BMAD
إذا كان المشروع يستخدم BMAD بشكل صريح، اقرأ الـ artifacts الموجودة واربطها بالـ Zoho: artifact → capability/epic → User Story → tasks/tests. استورد الجديد فقط، ولا تستبدل تعديلات يدوية في Zoho دون عرض الفروقات والموافقة.

## التقرير النهائي
أظهر نطاق Git الذي فُحص، التغييرات الجديدة، القصص والمهام المطابقة، العناصر المكررة التي تم تجاوزها، العناصر التي أُنشئت مع IDs، الحالات غير المؤكدة، العناصر Pending، وحالة checkpoint قبل التشغيل وبعده.
