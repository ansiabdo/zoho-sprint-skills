# دليل تشغيل تحليل Git وربطه بـ Zoho Sprints

## دورة التشغيل
**قراءة السجل السابق → التحقق من حالات Zoho → اكتشاف التغييرات الجديدة → تحليل diff → ربط القصص → فحص التكرار → مراجعة الخطة → تنفيذ معتمد → التحقق → تسجيل النتائج.**

### أول تشغيل
- إذا لم يوجد سجل، لا تفترض أن أي تعديل سابق قد تمت معالجته.
- اعرض baseline ونطاق الفحص المقترح، ثم اطلب تحديد ما إذا كان المطلوب تسجيل الحالة الحالية كنقطة بداية فقط أو تحليل نطاق تاريخي/تعديلات موجودة.
- لا تنشئ عناصر تلقائياً أثناء baseline غير المحدد.

### التشغيل المتكرر
- افحص العناصر المسجلة سابقاً في Zoho وحالتها الحالية أولاً.
- حلّل فقط commits والتعديلات غير المحاسبة بعد آخر checkpoint ناجح، مع فصل working tree عن commit history.
- عند تغيّر الفرع أو حدوث divergence، اطلب base ref أو نفّذ تقريراً فقط؛ لا تخمّن نطاق Git.
- لا تعاود إنشاء عنصر كانت نتيجة إنشائه غير مؤكدة قبل البحث والتحقق.
- احتفظ بالأخطاء والعناصر المعلقة في pending queue.

## قرار إنشاء عنصر
| الحالة | الإجراء |
|---|---|
| التغيير مغطى بقصة ومهمة مطابقة موجودة | ربطه بالعنصر الموجود وتسجيل أنه مغطى |
| القصة موجودة لكن المهمة الدقيقة غير موجودة | اقتراح/إنشاء Task أو Bug تحت القصة بعد التحقق من الإسناد والصلاحية |
| لا توجد قصة، والعمل يمثل قيمة مستقلة قابلة للاختبار | البحث عن المكرر ثم اقتراح User Story في Sprint مؤهلة زمنياً |
| لا توجد Sprint ضمن فترة البداية والنهاية الحالية | Pending؛ لا تستخدم Sprint مستقبلية أو منتهية |
| مطابقة ضعيفة أو متعارضة | لا تنشئ تلقائياً؛ اعرض البدائل واسأل |
| إنشاء Zoho انتهى بنتيجة غامضة | استعلم عن العنصر قبل إعادة المحاولة |

## ملاحظة مهمة
Git diff لا يثبت وحده أن العمل استغرق وقتاً طويلاً أو أن كل تعديل يتطلب مهمة. يمكن تسجيل تقدير أو مبرر الوقت فقط عندما يقدمه المستخدم أو تدعمه بيانات موثوقة؛ لا تخترع ساعات عمل.
