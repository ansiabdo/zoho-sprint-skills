# Workflow: Local Git changes → Zoho

Use [the policy contract](../references/policy-contract.md), [audit ledger](../references/audit-ledger.md), and [audit continuity](../checks/audit-continuity.md). Default to a review report. A specific instruction to create mapped items authorizes those writes only after the normal checks; otherwise present concrete proposed items before writing.

1. Confirm this is an actual Git repository and identify root, branch, HEAD, remote identity (with credentials removed), and any project-to-Zoho mapping. Load local state, ledger tail and pending actions before new diffs. Refresh recorded Zoho item statuses first.
2. Establish the delta since the last fully accounted checkpoint: committed changes, staged, unstaged and untracked work separately. If no valid checkpoint exists, label a baseline and state the range. If branch/history diverged, do not guess `HEAD~N`; produce a read-only unresolved-range report until a base is established.
3. Exclude secrets, keys, tokens, customer data, generated files, dependencies and binaries from content inspection. For allowed files, inspect diffs plus surrounding code; group changes by behavior and classify evidence, actual purpose, impacted module/API/data/UI/tests and attribution uncertainty. Do not assume a local change belongs to the current user. Do not mutate Git as part of analysis.
4. Read permitted Zoho Stories and children, all relevant sprint pages and the local ledger. Map each change group to existing work with high/medium/low confidence and evidence. Existing complete items can also cover work. A file name or commit title alone is weak evidence.
5. Propose a detailed child Task/Bug only under a verified Story assigned to the Developer. Propose a new Story only for independent user/business value after a broad duplicate check and the active/date-eligible sprint rule. A refactor or technical step does not automatically merit a Story.
6. Report each change, candidate Story, evidence/confidence, existing item/duplicate classification, proposed Task/Bug/Story, target sprint and blocker. Record write intent before any authorized create, then result and read-back. An ambiguous response stays pending; never retry automatically after a negative immediate search.
7. Persist the event ledger, pending queue and report. Advance the checkpoint only when every change is accounted for or durably pending with a safe replay plan. Report before/after checkpoint and all exclusions.

For existing mapped items, apply [actual delivery](document-actual-delivery.md) when requirements and observed implementation differ or delivery is partial. Preserve the old description, append evidence with a stable marker, and do not close an item or rewrite its requirements automatically. Apply [field completeness](../references/field-completeness.md) before any authorized write.
